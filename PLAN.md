## 2. Conflicts between the brief and the current app (decisions needed)

1. **Moving chances, cost and earnings behind Pro removes features free users have now.** That goes against "don't degrade the existing experience." See question Q1.
2. **Hidden planets can't be enforced while the browser holds every school and the scoring code.** Today the browser ranks all 203 schools locally, so it already knows #11–13. Truly hiding them means the server has to own something the client doesn't have. See question Q2.
3. **The About page promises "No sign-up, no cookies, no tracking" and "Close it and it's gone."** Saving to localStorage and adding accounts breaks both promises. The page has to be rewritten together with the privacy policy.
4. **Cloudflare Web Analytics has no custom events** (pageviews only), so the funnel events in section 5 need a different home. See question Q7.
5. **Magic links in TikTok and Instagram in-app browsers.** The email opens in Safari or Chrome, not inside the in-app browser. A PKCE link fails there because the code verifier lives in the other browser, and the anonymous sky in the in-app browser's localStorage isn't reachable either. **Plan:** make a 6-digit email code the main sign-in in in-app browsers. The user stays in the same browser, types the code and gets verified with `verifyOtp`. Keep the link as a fallback using the `token_hash` template so it works in any browser. Google OAuth is hidden in in-app browsers, because Google blocks embedded webviews.

## 3. Architecture

### 3.1 Frontend: refactor proposal (needs approval, see Q3)
- Move to **Vite** with ES modules. The five scripts become modules with the same code. The only changes are replacing `window.X = …` with `export` and `import`, plus moving the inline config into env.
- Why:
  - The engine needs to run unchanged in both the browser and a Supabase Edge Function (Deno) for server-side ranking and the gated Pro data.
  - Vitest for unit tests.
  - `import.meta.env` for the Supabase URL and anon key.
  - Lazy chunks keep the first screen light: `supabase-js`, Lemon.js and the account screens load only when needed.
- `data.js` becomes a module too. Pro-only fields get stripped from the public copy (see 3.3).
- **Parity check:**
  - Before the refactor, capture screenshots and DOM/fit snapshots at fixed steps (same answers, seeded RNG where possible).
  - After the refactor, capture them again and diff. Fit scores must match exactly.
- **Cloudflare Pages change:** build command `npm run build`, output `dist`. Branch pushes get automatic preview URLs, so we can test before merging.
- **TypeScript:** new modules stay plain JS with `// @ts-check` and JSDoc. Edge Functions use TypeScript, which Deno supports natively. I won't convert the existing JS to TypeScript without asking.

### 3.2 Backend: Supabase
- Auth: email code plus magic link, and Google OAuth. No passwords.
- Postgres, with RLS on every table.
- Edge Functions:
  - `lemon-webhook`: no JWT; signature-verified.
  - `sky`: computes the ranking and returns the gated Pro data.
  - `account-delete`: uses the service role.
- Scorecard import: extend the existing `scripts/build_data.py`. It already has verified field names, caching, rate-limit backoff and ID matching. It will upsert into `schools` and `school_pro` with the service-role key from `.env`, and still write the public `data.js`. Python avoids a rewrite, and it runs on your Mac today.

### 3.4 Payments: Lemon Squeezy (checked against the current docs)
- Checkout overlay via Lemon.js, opening a URL with:
  - `checkout[custom][user_id]=<uuid>`. It comes back in the webhook at `meta.custom_data.user_id`.
  - `checkout[email]` to prefill the email.
  - `checkout[discount_code]=<CODE>` when a creator code is stored.
- Affiliate script:
  ```html
  <script>window.lemonSqueezyAffiliateConfig = { store: '<slug>' }</script>
  <script src="https://lmsqueezy.com/affiliate.js" defer></script>
  ```
  The parameter is `?aff=` (`aff_ref` on manually built checkout links). Set the "Affiliate referral URL" to findyoursky.com. Build the checkout link with `LemonSqueezy.Url.Build()` so the referral carries into the overlay.
- Webhook:
  - Verify `X-Signature`, a hex HMAC-SHA256 of the **raw** body, with a constant-time comparison.
  - Events: `order_created`, and `order_refunded`, which also fires on **partial** refunds. Only a full refund revokes Pro; I'll confirm the exact status values from the Order object docs at the start of Phase 2.
  - Idempotent via `orders.lemon_order_id unique` and `on conflict`.
  - Return 5xx on failure so Lemon Squeezy retries.

## 4. Data model (`supabase/migrations/*.sql`)

```
profiles      id uuid pk → auth.users on delete cascade
              created_at, display_name, is_pro bool default false, pro_since,
              referral_code, friend_code text unique (generated by trigger, 8 chars, no lookalikes),
              confirmed_13_plus bool not null, gpa_unweighted numeric(3,2), sat_total int, act_composite int,
              income_bracket text check in Scorecard's 5 brackets
skies         id, user_id → profiles on delete cascade, created_at, version int,
              quiz_answers jsonb, profile_snapshot jsonb (major, region; no scores),
              results jsonb  ([{id, fit}] only; never chances or cost, since friends can read it)
schools       unitid pk, public fields, data_year, updated_at     (select: anon + authenticated)
school_pro    unitid pk → schools, net-price brackets, avg net, earnings, …   (no client grants; service role only)
orders        lemon_order_id unique, user_id → profiles on delete set null (pending Q5), status, amount, currency,
              referral_code, discount_code, refunded_at, created_at, raw_event jsonb   (no client grants)
friendships   requester_id, addressee_id, status pending|accepted, created_at,
              unique (least(a,b), greatest(a,b)), check requester ≠ addressee
events        name text check in allowed list, created_at, props jsonb (no ids, no PII)   (pending Q7)
groups, group_members   Phase 5
```

RLS and grants:
- **profiles**
  - select and update only your own row.
  - Column-level grants: `authenticated` can update only `display_name`, the academic inputs and `income_bracket`. `is_pro`, `pro_since`, `friend_code` and `referral_code` are never client-writable.
  - `referral_code` is set once by a `security definer` RPC `claim_referral(code)`, and only while it is null.
- **skies**
  - Owners have full access to their own skies.
  - Select is also allowed when an accepted friendship exists. Friends see only the latest sky, through a `friend_sky(friend_id)` RPC.
- **friendships**
  - Rows are created only through the RPC `request_friend(code)`, which resolves `friend_code` server-side so codes can't be enumerated and rate-limits requests.
  - The addressee accepts or declines; either side can delete (unfriend).
- **orders, school_pro**: RLS on, no policies, no grants. Only the service role can touch them.
- **Explicit RLS tests:** a script signs in two test users and asserts:
  - A can't read B's skies or profile.
  - A can't set `is_pro`.
  - A can read B's sky only after acceptance.
  - Nobody can read `orders` or `school_pro`.

## 7. Open questions

- **Q1. Free vs. Pro split.** Today chances, your-income cost and earnings are free on every card. Options:
  - **(Recommended)** Keep raw public facts free: admit rate, SAT range, sticker price and average net price. Make the *personal* answers Pro: your reach/target/likely, your-income net price, earnings, and the balanced-list builder. The deck pill and the balance warnings would become teasers for free users.
  - Or follow the brief literally and gate everything.
  - Or keep today's features free and make Pro only the new things: hidden planets, the builder and outcomes.
- **Q2. How "hidden" do hidden planets need to be?**
  - **(Recommended)** Pro searches a bigger pool. The 203 curated schools stay public, and the server holds an expanded Pro-only pool (e.g. about 1,000 more schools from Scorecard). Hidden planets are your best matches from that pool. This is truly enforced and adds real value. The catch: those schools don't have hand-curated flags, so they score on Scorecard data alone.
  - Or move all ranking to the server. That's truly hidden, but the quiz needs the network and loses its live motion offline.
  - Or soft-hide within the public 203. That's easy, but a devtools user could work them out.
- **Q3. Approve the Vite refactor** (section 3.1)? The alternative is staying build-free: load `supabase-js` from a CDN, keep config in a committed file (the anon key is public by design), and run tests with `node --test`. Sharing the engine with Deno would be clunkier.
- **Q4. Keep the account-free `#s=` friend links** alongside account friends? I recommend yes; it's the zero-friction viral loop.
- **Q5. Orders on account deletion.** I recommend keeping order rows with `user_id` set to null and `raw_event` stripped of the email, for refunds and tax records. Lemon Squeezy also keeps its own records.
- **Q6. Academic inputs.** I recommend keeping them free to enter, as they are today, and saving them to the profile only when signed in and only if you opt in.
- **Q7. Funnel events.** Options:
  - **(Recommended)** A tiny Supabase `events` table: anonymous inserts, an allow-listed event list, no IDs.
  - Cloudflare Zaraz `track()`.
  - Or pageviews only through Cloudflare Web Analytics.
- **Q8. Pricing check.** $4.99 minus Lemon Squeezy's fee (about 5% + 50¢; I'll verify in Phase 2) leaves about $4.24. A 50% affiliate commission (I'll confirm whether it's computed before or after fees) leaves you roughly $2.10 per referred sale. Is that intended?
- **Q9. Free #1 reveal for anonymous users?** The server computes your #1 from your answers, so someone could change their answers to get other reveals. I recommend requiring sign-in for the free reveal.
